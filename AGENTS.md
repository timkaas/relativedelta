# relativedelta

Date arithmetic in the style of Python's `dateutil.relativedelta`, for chrono, time and jiff. A public
crate on crates.io: every change is visible to its users.

## Checks

Every check is a prek hook in `prek.toml`; CI runs the same hooks. Before hand-off:

```sh
prek run --all-files                    # formatters and linters
prek run --all-files --stage pre-push   # tests, docs, licences, per-feature, no_std, MSRV
```

The repo's own pre-push hooks need a bare-metal target and the MSRV toolchain:
`scripts/no-std.sh install` and `scripts/msrv.sh install`.

## Facts

- `RelativeDelta` (`src/relativedelta.rs`) is backend-free. Each backend lives in its own module
  behind its feature (`chrono_impl.rs`, `time_impl.rs`, `jiff_impl.rs`) and implements the sealed
  `Shift` trait (`src/shift.rs`) plus the `+`/`-` operators. Features are additive: any combination
  of backends compiles, and every backend must behave the same.
- The crate is `no_std` unless the `std` feature is on; `serde` and `schemars` turn on `std`.
  `scripts/no-std.sh` and `scripts/feature-matrix.sh` guard this.
- The README and the guides in `docs/` compile as doctests with all features (`markdown_doctests`
  in `src/lib.rs`), so a code block that stops compiling fails the tests.
- The serialized shape of `RelativeDelta` is a public contract: users store it. Changing it is a
  breaking change.
- Releases: the human pushes a `vX.Y.Z` tag on `main`, and `.github/workflows/publish.yml` publishes
  that version to crates.io. Agents never tag or publish.
- Deviations from the standards, such as advisory ignores, are in `DECISIONS.md`.

## Core standards

Treat every repo as if it will be open-sourced: a skeptical senior engineer reviews each diff.

### Hard limits

- Work on a branch and hand off a PR; the human reviews and merges into `main`.
- Agents never deploy or run mutating cloud commands; read-only inspection is fine. Hand the human
  the command to run instead.
- Stop and escalate (options plus a recommendation) on: a contract change (GraphQL schema, DynamoDB
  key shape, Lambda input/output, env var names), IAM, auth or security, a new repository, a design
  decision with several valid options, or a fix loop that doesn't converge.

### Five musts (block hand-off)

1. All deterministic checks pass: format, lint, types, build, tests, docs, synth.
2. Behaviour is tested where it can go wrong: parsing, merging, algorithms, branching logic, edge
   cases. Every pure function on a request path has a unit test. Trivial tests are noise.
3. Zero dead, commented-out or unused code, and zero mid-migration leftovers (`foo2` beside `foo`,
   placeholder names like `struct PS`).
4. Contracts and invariants are preserved, or the change is escalated.
5. The hard limits above hold.

### Nine principles (the lower number wins a conflict)

1. **Everything earns its place.** Ask "why is this here?" of every construct: could it be deleted,
   inlined, borrowed instead of moved, or replaced by a library? Settle whether an item should exist
   before documenting or polishing it.
2. **One concept per module and type.** Responsibility lives with the data: state sits with the
   component that uses it, types construct themselves (`Planner::new(&graph)`), phases report results
   rather than choosing containers, shared context goes on `self`. Generic code knows nothing about
   its consumers. Visibility is minimal.
3. **Say it once.** One source of truth per fact; derive or generate the rest. Redundant state,
   duplicated construction logic and forwarding methods collapse into one.
4. **Let the types carry the rules.** Domain types over primitives, enums over magic values and
   `bool` flags, parse once into a structured type so later code can't fail, named structs over
   wide tuples. Make wrong use impossible by construction.
5. **Model the real concept, not today's case.** Abstract the policy, not the number; extract generic
   cores; name things for what they are.
6. **Less code.** A well-maintained library or tool beats hand-rolled code and beats patching a
   dependency. Current, supported runtimes.
7. **Cross-cutting concerns stay at the edges.** Tracing, caching and observability never shape the
   core data flow.
8. **Readable as a story.** Intent-revealing names, named intermediate results over nested calls
   (one step per line, each visible in a debugger), functional style where it reads clearer, small
   functions, comments only for the non-obvious why, actionable error context naming the runtime
   identifiers involved.
9. **Measure before optimising.** Benchmark first, one change at a time, report what caused each gain.

Rules a principle conflicts with are fixed, or defended in `DECISIONS.md`.

### Working with the human

- **Fidelity.** Follow the agreed plan or spec exactly. A deviation that gains something is recorded
  in `DECISIONS.md`; anything else goes back as a question.
- **Scope.** Touch only what the task needs; list anything else as "left unchanged, needs a broader
  decision". Format and check only changed files.
- **The human's choices stand.** Keep what the human wrote unless asked; explain any removal. Accept
  staged solutions the human picks ("cloning is fine for now") and record the follow-up.
- **The human designs the types.** Propose the type skeleton (newtypes, traits, enums, signatures)
  for approval before bulk implementation, and list the idiom choices made. Asked an idiom question,
  explain the trade-offs rather than rewriting the code.
- **A discussion is not a change.** A design question ends as code or a `DECISIONS.md` entry. A
  request to discuss ("do not write any code") gets analysis and examples only.
- Prefer suppressing a lint with a reason over making the code worse to satisfy it.

### Defaults when not asked

- Unit tests for logic that can go wrong.
- Documentation as the stack's pack says.
- READMEs, examples, new markdown files and schema fields only when the task asks.
- **Dependencies** are added freely when widely used, released within 12 months with triaged issues,
  under a licence in the allowlist in `.lunapinc/deny.toml`, and free of open advisories; each gets a
  line in `DECISIONS.md`. Anything else is escalated.

The reasons and incidents behind these rules: `evidence-log.md` in `LunaPinc/standards` (private).

## Rust pack

Write Rust the way an expert in its idioms would, held to the Rust API Guidelines, with every
choice legible to a human who wants to question it.

- **Idiomatic first.** Follow the API Guidelines and community conventions, and make clippy
  pedantic pass. The core principles are the lens for every structural choice.
- **The standard traits are the vocabulary.** Conversions through `From`/`Into` and
  `TryFrom`/`TryInto`; parsing through `FromStr`; `Display` for user-facing text; `AsRef`/`Borrow`
  for cheap views; `Default`, `Iterator`/`IntoIterator` and `Error` where they fit. Derive the common
  traits (`Debug`, `Clone`, `PartialEq`, `Eq`, `Hash`, `Ord`, `Default`, serde) whenever the type
  supports them. An inherent `to_x`/`from_x`/`parse` method that a standard trait already names is
  that trait instead.
- **A newtype exposes only what its concept needs**, through explicit methods and the standard
  traits. `Deref` belongs to smart pointers; a newtype that derefs to its inner type leaks the
  representation it was made to hide.
- **Crates for sub-problems.** A well-maintained crate that solves a sub-problem beats hand-rolled
  code: `thiserror`, `strum`, `itertools`, `secrecy`, `url`, `chrono`, `derive_more` and their peers.
  The core's dependency bar applies.
- **Signatures are explainable:** `impl Into<String>` vs `&str`, borrowing vs cloning `Arc`-backed
  clients, blanket impls for `T` and `&T`, generics and borrows over forcing `Arc`, `dyn` or
  `'static` on callers. A builder once an entry point gains several optional knobs. Be ready to
  justify each choice in a sentence.
- **Advanced constructs come broken down.** Macros, typestate, trait-heavy generics and lifetime
  puzzles are welcome when they earn their place. Split them into named, documented pieces, each
  small enough to reason about alone, with the why in the doc comment, so the human can question
  and improve any part.
- Exhaustive `match` over closed sets. Cargo features are additive; behaviour choices are type
  parameters or options. Production paths are free of panics, needless clones and hidden mutable
  state.
- Errors: `thiserror` types in libraries, `anyhow` with `with_context` at the edges.
- **Library crates** are documented per the Rust documentation pack, which library repos carry.
  **Binaries** get module-level docs and docs on non-obvious items.
- **Tests** cover this crate's behaviour, not its dependencies'. AWS clients are injected and mocked
  with `aws-smithy-mocks`; `fake` generates test data; real payloads seed fixtures when available.
- Private LunaPinc crates are git dependencies on `ssh://git@github.com/LunaPinc/<crate>.git`, with
  `[net] git-fetch-with-cli = true`. Use that exact URL form everywhere: cargo treats one crate from
  two URLs as two different crates.

## Rust documentation pack

Library crates are documented to open-source standard (RFC 1574, the Rustdoc Book and the API
Guidelines), so a user can work with the public API without reading its implementation.

- **Lints:** `#![deny(missing_docs)]` and `#![deny(rustdoc::broken_intra_doc_links)]` at each crate
  root. `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps` and `cargo test --doc` pass, with examples
  tested under the relevant feature sets.
- **Crate root:** what the library is for, its main concepts, a quick-start example, the important
  modules and their responsibilities, and its feature flags.
- **Modules:** their responsibility and place in the library, the relationships between their parts,
  and typical usage where it helps.
- **Types:** purpose and intended use, invariants and guarantees, ownership and lifecycle where they
  matter, and what notable trait implementations imply.
- **Functions and methods:** a summary starting with a third-person verb ("Returns…", "Creates…");
  behaviour the signature doesn't show; `# Errors`, `# Panics` and `# Safety` sections whenever they
  apply; an example where it helps. Parameters get prose only for semantics the signature leaves
  open: units, ranges, constraints, ownership.
- **Examples** are complete and realistic, compile as doctests, propagate errors with `?`, and show
  typical use and the edge cases that matter.
- **When relevant**, document complexity and performance, allocation, thread safety, feature flags,
  MSRV and platform limits, and error recovery.
- Intra-doc links (`[`Type`]`) for every reference to another item. Describe observable behaviour,
  not the implementation.
- Package metadata (description, licence, repository, keywords) meets crates.io standards.
